# Test a 42 project

Use this skill to run ftorture, not to modify its test framework. The Python CLI delegates to registered project modules and the C engine; do not invoke internal modules or generated binaries as the normal entry point.

## Discover and prepare

```bash
torture --list-projects
torture --help
```

- Current modules support **libft v19.3**, **ft_printf v12.1**, **get_next_line v14.3**, **push_swap v1.2** (the new subject with `--simple/--medium/--complex/--adaptive` and `--bench`; the old one without selectors fails the strategy and `--bench` suites by design), **python-module-00 (`py00`) v3.0** (*Growing Code*), and **python-module-01 (`py01`) v3.2** (*Code Cultivation*). Verify the student's actual subject before interpreting a mismatch. The registry in `ftorture/projects/__init__.py` is authoritative for this checkout.
- User suites are discovered from `${XDG_CONFIG_HOME:-$HOME/.config}/ftorture/tests/*.json` or `--custom-tests-dir DIR` and listed as `custom-<key>` / `[CUSTOM]`. They are user-owned commands, not official subject checks; only run trusted manifests. See `docs/custom-tests.md`. They require no C tools unless their own commands do.
- Requirements: Linux, Python 3.10+. C projects also require a C compiler and their build tools (`make`/`nm` for archive/executable projects; `nm` for GNL). Python modules (`py00`, `py01`) require no C tools. `norminette` (C), `flake8`, and `mypy` (Python) are optional. There are no Python package dependencies.
- Install with `python3 install.py`, then use the installed `torture` command from any directory. The installer writes a Python launcher directly to `~/.local/bin/torture`, detects the running shell and checks its startup file. If PATH setup is missing it shows instructions and asks before editing; declining or non-interactive installation never edits shell configuration. If `torture` is "not found" right after accepting PATH setup, the current shell has not reloaded its startup file yet (open a new terminal or `source` the shell startup file). Keep the checkout in place for the launcher's Python code and C suites. No aliases, shell wrappers, network access, or root permissions are needed for tests; direct Python entry points are development/test interfaces, not the normal user workflow.
- Confirm the student directory and expected layout. libft/printf/push_swap require a Makefile (push_swap is detected by `NAME = push_swap` in the Makefile, before any `ft_printf.h` or `libft.h` it ships); GNL is compiled from sources; Python modules are auto-detected from their exercise files (`ex0/ft_hello_garden.py`, `ex0/ft_garden_intro.py`, …). Inspect the student's working tree: archive/executable builds/checks run `make fclean`, `all`/`bonus`, and a final `make fclean` (even after an error or Ctrl-C), so objects **and** the archive (push_swap: `push_swap` and `checker`) are removed at the end. Python modules run with `PYTHONDONTWRITEBYTECODE=1` and never write `__pycache__` or modify student files. Ask first if existing artifacts must be preserved. Do not change student source unless explicitly asked.

## Run and narrow failures

Use explicit project and directory arguments for automation; quote paths with spaces. With no project argument in a terminal, the original retro menu offers project selection (arrows, j/k, or `1..N` shortcuts; Python modules are grouped under one PYTHON MODULES entry that opens its own menu, `q`/BACK returns), an editable path with Tab completion, and option checkboxes (`-s`, `-v`, `-e` for C projects, checks, `-c` chill mode, norminette or `flake8 / mypy`, and `--no-hidden`). CLI options initialize those checkboxes; Space toggles them and Enter on the launch row starts testing.

```bash
torture libft /path/to/libft -f strlen,split -v --lang en --no-color
torture printf /path/to/ft_printf -p 1 -f %d,%s -v
torture gnl /path/to/get_next_line -p 1 -f 1,42
torture push_swap /path/to/push_swap -f errors,perf500 -v
torture py00 /path/to/python-module-00 -f ex0,ex7 -v
torture py01 /path/to/python-module-01 -c -v
```

- Omit `-f`/`-p` for full coverage. `-f` selects libft functions, printf suite keys/conversions/labels, GNL buffer sizes (`def` means no explicit size), push_swap suite keys, or Python exercises (`ex0`, `0`, `ft_plot_area`). Prefer stable printf keys such as `pf_d,pf_minus` when labels may be translated.
- push_swap suite keys: `args errors sorted small simple medium complex adaptive bench perf100 perf500` (part 1) and `checker ck_errors` (part 2, needs a `bonus` rule that builds `./checker`).
- `-p` selects a part: libft 1–3; printf/GNL/push_swap 1 mandatory, 2 bonus; Python modules 1. Missing bonus support is not a pass. Printf needs a Makefile bonus rule; GNL needs the complete bonus file set.
- Use `--seed N` to reproduce fuzzing, `--timeout S` for per-test timeouts, `-e [N]` / `--efficiency [N]` for the C efficiency gauge (target N%, default 50), `-t N` / `--target N` to change the target (it turns `-e` on), and `--lang en|fr` to override locale detection.
- `-c` / `--chill` downgrades soft style/hygiene check KOs (extra files, README, norminette, unused/duplicate includes, Makefile hygiene, `flake8`, `mypy`, type annotations, Python naming) to `▲` warnings so behavioral failures stand out; combining `-c -s` makes those warnings fail again.
- `--repro TEST` (C suites only) rebuilds one failing test alone with `src/repro.c` and the student's code and runs it under valgrind (or plain if valgrind is absent); add `--gdb` to launch it under `gdb`. The exact `--repro` command is printed under each failure when running with `-v`.
- `--no-hidden` ignores dot-files and dot-folders (`.vscode`, `.DS_Store`…) in extra-file, include-use and norminette checks. `--no-norm` disables norminette (C) or `flake8`/`mypy` (Python); `--no-checks` skips all subject checks but still builds/runs tests. A passing unchecked run does not validate the submission structure.
- Run serially per checkout: a lock protects shared artifacts and the report. Copy relevant logs before another run overwrites them. Installation updates are a separate action (`python3 install.py --update`), not a prerequisite for diagnosing student code.
- Uninstall only when requested: `python3 install.py --delete --confirm`. Both flags are mandatory. The installer refuses unrelated commands and preserves shell PATH entries, the checkout, and custom tests.

## Diagnose and report

| Evidence | Location / meaning |
|---|---|
| Native checks | `build/<project>/checks.txt`; file, Makefile, README, norm, include, symbol, prototype verdicts |
| Check diagnostics | `build/<project>/checks/`; numbered tool logs and generated compiler probes |
| Build/link diagnostics | `build/<project>/make.log`, `link.log`, and per-pass subdirectories; use the exact path printed by the runner |
| Detailed test report | `ftorture.log` at the checkout root; `-v` also prints failure details |
| Exit status | `0` selected tests/checks pass; `1` test/check failure; `2` runner/build error; `130` interrupted |

- Distinguish build errors, failed subject checks, and behavioral failures. `✔` passes; cyan `✔` is an accepted reference-matching crash. `✘` fails; `S` crash, `T` timeout, `L` leak, `M` malloc-failure protection failure.
- `▲` is speculative and does not fail by default; `-s` makes it count. Never label undefined/reference-dependent behavior a required subject violation without checking the specification.
- **Extra files are KO** (not a warning): anything that is not a file to submit, hidden files except `.git`/`.gitignore`, unexpected extensions (`.py`, `.cpp`, `.txt`, `.o`, `a.out`, `.swp`…), empty folders. ft_printf may keep a `libft/` folder (`*.c`, `*.h`, `Makefile`); when `libft/libft.a` exists its symbols join the `nm` check (libft functions are allowed, libft externals checked the same way) and "libft in the archive" is KO if `libftprintf.a` leaves `ft_*` calls that only `libft.a` defines (linking libftprintf.a alone fails; the tester itself still links libft.a so behaviour tests run). libft (`ft_*.c`, `libft.h`), ft_printf and push_swap (`*.c`, `*.h`) may use subfolders such as `srcs/` and `includes/`: `Project.find_header` looks at the root, then the shallowest match (depth ≤ 4, gitignore-aware), and every folder holding a `.h` becomes a `-I` for include and prototype checks; Makefile, README and archive stay at the root. GNL (`nested=False`) requires its files at the root. Anything matched by the folder's `.gitignore` files (root and nested, git semantics: `!`, `**`, anchored `/`, `dir/`, no re-include inside an ignored folder) is never pushed, so it is skipped by extra-file, include and norminette checks in every project; the "Extra files" detail says "(N ignored by .gitignore)". If a submitted file is unexpectedly missing from the checks, look at the `.gitignore` first. If the only KO is an editor folder the student will not submit and did not gitignore, rerun with `--no-hidden` to confirm the rest.
- **Bonus file names**: with a `bonus` rule, the `.c` files in `make -nB bonus` but not in `make -nB all` (recursive makes matched by trailing path) and the project headers only they reach must end in `_bonus.c` / `_bonus.h` (KO, softened by `-c`); files shared by both builds keep their name. push_swap only gets ▲ (its subject lists `*.c, *.h` for the checker). GNL already requires its `_bonus` names.
- **Unused `#include` are KO**: a `<lib.h>` must give the file at least one name it uses (function, type, macro, enum constant); a project `"x.h"` must give one of its own declarations or of the libs it includes; a header's includes also count for the files that include it. `NULL`, `size_t`, `ssize_t`, `va_list`… only justify the **first** include of a file that gives them, so `<stdio.h>` kept only for `NULL` is reported. Duplicate includes are KO too. Include-use analysis is heuristic; unresolved headers get no verdict, and complex macros/conditional compilation warrant manual review.
- **GNL with small `BUFFER_SIZE`s**: the 100 000 / 300 000 character lines are cut to 4096 `read()` calls (`LONG()` in `src/gnl/t_gnl.c`), so a quadratic stash (a `strjoin` after every `read()`) still passes them quickly; the real 100 000 line runs in the ▲ test "ligne de 100 000 en moins de 3 s", which stops itself after 3 s with an explanation. A ▲ there plus a low `-e` score = correct but quadratic, not a bug. A `T` elsewhere is a real timeout.
- **GNL Bible test**: every pass reads the King James Bible (`data/bible-kjv.txt.gz`, decompressed into `build/gnl/`, `-D Z_BIBLE`): whole book for BUFFER_SIZE 32–10 000 and `def`, the first `BUFFER_SIZE × 50 000` bytes below 32, the first 100 KB above 10 000. A `T` there with a large buffer and nowhere else usually means the stash is copied/moved after every line.
- **GNL custom inputs**: `-f` takes any BUFFER_SIZE list (`3,77,100k,10M,def`; sizes outside the usual 14 get slots `bsc1..8`, also run in the bonus). `--file PATH|SIZE` (repeatable, comma-separated, max 16, sizes `64k`/`2M` up to 256M) runs **only** those inputs: a text file compared line by line with its content (a `\0` byte is rejected), or a generated file (random lines 0–200 chars, one of 10 000, last without `\n`). Its default timeout is `10 s + size / min(BUFFER_SIZE, 4096) × 10 µs + 50 ns/byte`, capped at 600 s; `--timeout` overrides it. (An old memtrack false positive, "free() d'un pointeur au milieu d'un bloc malloc" after ~300 000 mallocs, is fixed; if it ever reappears, suspect the tracker before the student.)
- **push_swap**: ftorture runs the student's binaries from Python (`ftorture/projects/push_swap_tests.py`, killed on timeout, default 20 s per run) and replays stdout on its own stack simulator: anything but `sa sb ss pa pb ra rb rr rra rrb rrr` one per line, a missing final `\n`, or `a` not sorted / `b` not empty is ✘. KO thresholds are the subject's minimum (100 numbers < 2000, 500 < 12000, 5 seeded lists each), except a list whose disorder is in the medium regime (0.2–0.5, where --adaptive must use its O(n√n) method): over the limit there is ▲ via `zft_soft()`; with `checker_linux` (`--checker PATH`, the project folder, `~/Downloads`; copied executable into `build/`) every perf sort and `-e` measure must also get its OK; "good"/"excellent", 3 numbers ≤ 3 and 5 numbers ≤ 12 moves, the complexity growth (`ops ~ n^e` between 100 and 400 numbers: medium ≤ 1.75, complex/adaptive ≤ 1.4), distinct strategies, `"3 2 1"` as one argument, `""`, `+1 1`, `0 -0` and unknown flags are ▲. `--bench` must keep stdout identical and print on stderr the disorder with 2 decimals (rounded or truncated), the strategy name, `O(`, the total and the 11 operation names. Checks: valgrind (`valgrind` in PATH, else SKIP) on sorts, errors, `--bench` and the checker (leak/invalid access ✘, still reachable ▲), `nm` limited to the `.o` files the Makefile produced (a visualizer or CMake build in the folder is ignored there but still KO in extra files), allowed `read write malloc free exit`, static globals ▲, README with both logins and contributions ▲.
- **Valgrind**: libft, ft_printf and GNL also run under memcheck (`ftorture/valgrind.py`): student sources rebuilt with `-g -O0` (GNL: compiled with `-g`), memtrack off via `FTORTURE_SAN_DIR`, each child writes `pid<pid>` so `vg.<pid>` maps to its test (`build/<project>/valgrind/<name>/`). Invalid read/write, uninitialised values (use site + creating malloc via `--track-origins`), invalid/mismatched free and overlap in student frames are ✘; NULL (+<4096) addresses, the libc reference child, tests whose normal verdict was a libc-matching crash and leaks are not reported. GNL: BUFFER_SIZE 1 and 42 only; the Bible, the 10 000 / 100 000 / 300 000 lines, the big file and the 5 000 lines are skipped with the engine's `--skip-name` (a quadratic stash at BUFFER_SIZE=1 made the 10 000 line alone take 15 s under memcheck). `--no-valgrind` skips it.
- **Sanitizers**: each C project also runs (in the background from the start, results shown before the summary) with the student's sources rebuilt with `-fsanitize=address,undefined` (no memtrack, so ASan sees the heap; `null`, `nonnull-attribute` and `pointer-overflow` are left out because the NULL tests compare crashes with the libc). Test verdicts of that pass are ignored; each report (per test: `build/<project>/sanitize/*/t<seq>.<pid>`, `tests.tsv` maps seq to the test) becomes a SANITIZERS line `function  file.c:line · message` + the first test: ✘, or ▲ if only in speculative tests. UBSan runs in recover mode, so a signed overflow is ✔ "cancels out" when every normal (non-speculative) test it happens in passed in the normal pass (`renderer.results[(suite, index)]`; push_swap: same output as the normal binary), and ✘ otherwise; out-of-bounds never cancels. Typical: `ft_atoi` accumulating a positive int then `* -1` on `-2147483648` (cancels out, ✔), `ft_itoa` doing `-n` on INT_MIN with a wrong result (✘), `ft_itoa`/`ft_putnbr` doing `-n` on INT_MIN, one-byte stack overflows that never crash. `--no-sanitize` skips it (CLI only).
- **Speed / waiting**: valgrind and the sanitizers start in the background before the checks (libft, ft_printf, GNL: everything, push_swap: during the suites), one process per core; a "▶ valgrind + sanitizers… N/M" line means results are still coming, not a hang. Full runs on a 20-core machine: libft ~6 s, ft_printf ~4 s, GNL ~10 s, push_swap ~5 s. With `-e` nothing runs in the background while the code is timed (slower, but the timings stay right). `--no-valgrind` / `--no-sanitize` give the fastest feedback loop while fixing a bug; rerun without them before concluding.
- **Efficiency (`-e`)**: each function line gets `⚡ N%` and the result box ends with a gauge (geometric mean, each value clamped to [1%, 200%]) with a `┃` mark at the target, the functions below it and the main machine costs. N% = **perfect time / real time**. There is no reference implementation: each workload declares with `COST()` the minimal work a perfect implementation cannot avoid (bytes scanned/copied once, one `write()` per string, one `read()` per `BUFFER_SIZE`…), and ftorture prices each unit on the current machine (tightest `-O0` loop, L1-sized data, best of 20). A typical clean libft is around 60–100%; a little over 100% is calibration noise. It is information only and never makes a run KO; runs differ by a few %. Typical low scores: `write()` per character (`ft_putstr_fd`, `ft_printf`: 1–5%, a syscall is ~600 ns), length-then-copy (`ft_strlcpy` ~40%), `ft_lstmap` walking to the end for each node (~2%), a GNL `strjoin` stash or a `BUFFER_SIZE` buffer allocated at every call (1–3%). GNL is not measured without `-D BUFFER_SIZE`. `ftorture.log` lists perfect vs real time per function and all machine costs; `FTORTURE_BENCH_DEBUG=1` prints them live. Present a low score as a performance remark, never as a subject violation. For push_swap, `-e` is **not a time**: `SCORE()` averages the default strategy's operation count over 20 lists of 100 and 8 of 500 numbers; 100 % = the subject's "excellent" threshold (700 / 5500), so the 50 % default target means 1400 / 11 000 operations.
- **Python modules (`py00`, `py01`)**: every behavioral test runs in an isolated `python3` subprocess (`PYTHONDONTWRITEBYTECODE=1`, private process group, per-test timeout, default 5 s). Native checks (`build/<key>/checks.txt`) validate required/extra files (`.gitignore`-aware, `--no-hidden`), Python syntax (`ast.parse`), `flake8` (soft, SKIP if absent or `--no-norm`), `mypy` (soft, SKIP if absent or `--no-norm`), AST type annotations (always checked even without `mypy`: required on `ex7` for `py00` and all exercises for `py01`), module structure (`py00` forbids top-level code and `if __name__ == "__main__":`; `py01` requires `if __name__ == "__main__":` on `ex0` and allows it on `ex1`–`ex6`), authorized built-ins/imports per exercise, and naming conventions (`PascalCase` classes, `snake_case` functions on `py01`). `--repro` and `-e` are C-only and do not apply to Python modules.
- Report the exact command, project/subject version, exit status, failing check/test, input, expected/actual result, speculative status, relevant log path, and smallest rerun. A filtered pass is not a full-project pass. Do not weaken tests or silently alter the student's submission to improve results.
